Architecture

Source discovery reads databases and documents through registered access paths. The original systems own their facts. GitLab owns the history of source-bound configuration and canonical business definitions; snapshots and HTML are derived read-only evidence. Agents submit checked inputs, CI runs automatically, and the publisher independently verifies the exact reviewed revision before release.

Four boundaries organise the implementation:

  • Source systems are read-only. Connectors take; nothing writes back through them. A figure that appears in two independent systems is corroborated because they cannot have copied from us.
  • Bound values come from the source. The spec states where to read; values arrive through the checked read path. Version definitions and reasoning in git. Inline values in synthetic examples are fixtures; phase-one projections reject authored records and formulas.
  • Relationships are generated, never synchronised. Anything stated twice can disagree with itself, so it is stated once and derived everywhere else.
  • Writes state their intent and require authority. Model proposals use the managed GitLab path; authors cannot push to the protected target or install different CI. Source changes require their own reviewed migration and executor.

The GitLab/runner/publisher path has passed actual isolated Docker deployment acceptance, including revision-bound review, rollback, artifact integrity and membership revocation. The source Gateway and its Nexus authority adapter are implemented separately. Dotted connections show work that is not connected in this managed deployment: customer Nexus SSO and approved source write-back. GitLab authenticates model reviewers; Nexus remains the source/data authority. Neither permission domain is replaced by a graph menu or a YAML approval flag.

The current Northwind ShareOne URL is a separately hosted static review artifact, not a customer login deployment or an automatic destination of the GitLab fixture. See installation and interfaces, the acceptance evidence, and the broader design at §7.14 for deployment choices inside a customer's network.

Hands-on review after architecture alignment

The previous disposable acceptance stack has been removed. This discussion page is not a running GitLab workspace or a login screen. Start a separate installation using the deployment instructions before attempting the following review.

  1. An authorised agent reads the registered contract and submits a model change with intent.
  2. Inspect the resulting GitLab merge request, exact commit and automatically generated CI review artifact. Successful CI alone must not publish the proposal.
  3. As the independent reviewer, inspect the draft and approve that exact revision in GitLab.
  4. Confirm the publisher independently checks and compiles it, merges the reviewed revision and serves the accepted reader with a verifiable receipt.
  5. Check that a new commit needs a new review; try a reviewed rollback and verify that definitions retain their identities.

The deployed acceptance record proves the technical path on synthetic data. Human hands-on review is still needed to establish that the interaction matches the intended workflow.
