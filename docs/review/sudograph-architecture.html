Architecture

Source discovery reads databases and documents through registered access paths. The original systems own their facts. One canonical model owns definitions and references. Its checked edits automatically produce the review graph and context; no GitLab approval is required for each modelling turn. GitLab reviews executable production source-change plans. Version history and optional artifact delivery must not become an additional business-editing gate.

Four boundaries organise the implementation:

  • Discovery and review read source systems. Editing a definition does not mutate its source. Production writes require the separate planned path below; read access does not grant write authority.
  • Bound values come from the source. The spec states where to read; values arrive through the checked read path. Version canonical definitions and evidence. Inline values in synthetic examples are fixtures; phase-one projections reject authored records and formulas.
  • Relationships are generated, never synchronised. Anything stated twice can disagree with itself, so it is stated once and derived everywhere else.
  • Model editing and production effects have different boundaries. Model edits require authorisation, compiler checks and revision/conflict handling. They do not require GitLab human approval. Production source changes need an exact reviewed plan, operation grants and executor checks.

The solid paths describe the intended model loop and its existing compiler, renderer and context components; the complete host loop is not deployed. The optional GitLab model-publishing prototype passed isolated Docker acceptance for revision review, rollback, artifact integrity and membership revocation. It remains available, with its existing checks, while the default authoring adapter is integrated. This prototype is not a production database-write gate. The source Gateway and Nexus authority adapter exist separately. Dotted paths show planned production execution and SSO integration. Main-LLM context compression is also planned; only deterministic context generation exists today. Graph menus and YAML flags cannot grant source or production execution authority.

The current Northwind ShareOne URL is a separately hosted static review artifact, not a customer login deployment or an automatic destination of the GitLab fixture. See installation and interfaces, the acceptance evidence, and the broader design at §7.14 for deployment choices inside a customer's network.

Hands-on review after architecture alignment

The previous disposable acceptance stack has been removed. This discussion page is not a running GitLab workspace or a login screen. The host integration must support the following journey.

  1. An authorised agent submits a model edit with its base revision and operation ID.
  2. The compiler refuses invalid inputs with repair diagnostics; a valid edit updates the canonical revision and generated graph without GitLab approval.
  3. Business people discuss the definition through the graph or bound chat; agreement and unresolved issues retain their evidence and scope.
  4. Any authorised agent reads the same versioned knowledge and exact pointers. Optional main-LLM compression remains derived from that revision.
  5. A requested production source correction follows a separately reviewed executable plan and authorised executor; ordinary model edits do not write to the source.

The deployed acceptance record proves the optional GitLab model-publishing prototype on synthetic data. It does not prove the default host editing loop or production source write-back. See its deployment instructions only when evaluating that optional delivery path.
